# IEDSyncTogether v0.3.1 ActorBlock probe

v0.3.1 keeps the validated LAN synchronization and IED Custom Item renderer from v0.3.0. It adds one targeted experiment using only IED's public Papyrus API.

## Purpose

The v0.3.0 dual-client test proved that remote snapshots are captured, transmitted, resolved to the correct STR proxy, and rendered as IED Custom Items. It also proved that the proxy's stock IED/STR equipment layer remains visible, producing duplicates such as Kahel's shield appearing both equipped and on the synchronized back node.

v0.3.1 tests whether `IED.AddActorBlock` can suppress the stock NPC equipment layer while leaving IEDSyncTogether-owned Custom Items visible.

No private IED runtime hook is installed or reintroduced.

## Behaviour

When `SuppressRemoteNpcDisplays=1` and a LAN peer is bound to a resolved STR proxy, the probe periodically queues:

```text
IED.AddActorBlock(proxy, "IEDSyncTogether.esp")
IED.Evaluate(proxy)
```

The block is reasserted every 750 ms because the existing Custom Item renderer legitimately calls `RemoveActorBlock` before rebuilding its owned items. This is intentionally a diagnostic implementation, not the final architecture.

When a proxy disappears, the save is changed, or the session is reset, the probe queues `RemoveActorBlock` and evaluates the actor again.

## Test protocol

Install the same v0.3.1 build on both STR clients and leave `SuppressRemoteNpcDisplays=1` in `IEDSyncTogether.ini`.

Connect both players and observe each remote proxy.

There are three meaningful outcomes:

1. Stock proxy equipment disappears and synchronized Custom Items remain visible.
   This validates `AddActorBlock` as the basis for the final suppression implementation.

2. Stock proxy equipment and synchronized Custom Items both disappear.
   `AddActorBlock` is too broad; the next step must use a more selective public IED integration path.

3. Nothing changes and stock equipment remains visible.
   The ActorBlock API does not affect the STR proxy path involved in the duplication, so this approach is rejected.

## Relevant log lines

Expected startup lines:

```text
IEDSyncTogether v0.3.1 loading
IED integration mode: official Papyrus Custom Item API + public ActorBlock probe; no IED runtime patch installed
IED v0.3.1 ActorBlock probe started
```

For each resolved proxy:

```text
IED ActorBlock probe active: proxy=XXXXXXXX AddActorBlock+Evaluate accepted=1
IED ActorBlock probe dispatch: proxy=XXXXXXXX action=add blockAccepted=1 evaluateAccepted=1
IED Custom Item render queued: proxy=XXXXXXXX slots=N dispatchAccepted=1
```

`accepted=1` means the Papyrus calls were accepted for dispatch. It does not by itself prove how IED applied the block; the visual result is the decisive part of this probe.
